# R³∞ System One — CLM transition / Jev fallback

Date: 2026-09-29
Owner / Vision: Claudio Terzi
Status: CANDIDATE PATCH — branch `candidate/clm-systemone-20260929`

## Decision

R³∞ no longer treats Jev as the only canonical System One backend.

The canonical object is now the **System One layer**: one shared policy/transport surface for fast typed judgments. It may be served by:

- **CLM-v0.1-8B** when a CLM endpoint is deliberately configured;
- **TypeSafe/Jev** as fallback/reference backend;
- future compatible System One backends only through the same shared transport and policy layer.

No second global decision engine is created.

## Why CLM is promoted to preferred candidate

The official CLM release (2026-09-23) exposes a TypeSafe-compatible `POST /v1/systemone` API with Choice / Score / Noul and adds a native `POST /v1/rank` primitive.

The release reports:
- CLM-8B: frozen Qwen3-8B encoder plus contrastive state/action projection heads;
- pre-training on ~60M Nemotron Q&A pairs, ~30M synthetic hard negatives, ~1M agentic trajectories;
- performance reported as comparable to Jev on computer-use, gaming and tool-calling with up to 9x lower latency;
- lightweight downstream fine-tuning of the heads;
- Apache-2.0 weights and self-hosting.

These are upstream claims and do **not** prove CLM is universally better than Jev. A small independent field test published after release found a relatedness task where Jev substantially outperformed zero-shot CLM. Therefore the migration rule is **benchmark, then promote per domain**, not blanket replacement.

## Architecture

```
Raffaello / project
    -> bounded state
    -> canonical R3 System One policy
    -> provider router
         -> CLM (preferred when configured)
         -> TypeSafe/Jev fallback
    -> Choice / Score / Noul
    -> optional CLM native Rank
    -> P5/P6 + deterministic code + real evidence
    -> decision / verification / authorized action
```

## Provider router

`typesafe_sister/client.py` remains the single transport module for backwards compatibility.

New safe configuration:

- `R3_SYSTEMONE_PROVIDER=auto|clm|typesafe`
- `R3_SYSTEMONE_BASE_URL`
- `R3_SYSTEMONE_MODEL`
- `R3_SYSTEMONE_API_KEY`
- `CLM_BASE_URL`
- `CLM_MODEL` (default `clm-latest`)
- `CLM_API_KEY` (optional for self-hosted CLM)

Legacy `TYPESAFE_*` variables remain valid.

`auto` selects CLM only when a CLM endpoint is explicitly configured. Otherwise it falls back to TypeSafe/Jev when its key is present. This prevents a silent dependency change.

## New capability: native Rank

CLM's `/v1/rank` is exposed centrally as `typesafe_sister.client.rank`.

Use cases:
- best next evidence path;
- best tool/action among candidate actions;
- retrieval shortlist reranking;
- verifier over candidate plans/trajectories;
- Bitcoin Cannes 2009 forensic information-gain routing;
- project-patch selection before expensive evaluation.

The rank primitive is **not emulated on Jev**. If the active backend is Jev, callers receive an explicit capability-unavailable error. This preserves epistemic honesty about what was actually executed.

## Migration rule

For every existing Jev domain pack:

1. preserve the same state and rubric;
2. collect a representative held-out set with real labels or verified outcomes;
3. run Jev and CLM independently;
4. compare accuracy/calibration, latency, failure modes and cost;
5. promote CLM for that pack only if equal-or-better verified utility is demonstrated;
6. keep Jev as fallback until CLM has passed the pack gate;
7. never use model score to authorize external actions.

No score gaming: wording-only changes do not count as improvement.

## Bitcoin Cannes 2009

The new CLM Rank primitive is especially relevant to the recovery investigation.

Candidate actions/evidence paths can be generated by Raffaello and ranked by information value, e.g.:

- Barclays historical transaction / merchant descriptor;
- PayPal history;
- Fabrizio contemporaneous email;
- Santoni IT backup / disk image;
- historical Bitcoin seller record;
- wallet/client artifact;
- blockchain linkage.

CLM/Jev may prioritize and falsify hypotheses, but they do not prove ownership, recover keys, access private systems or replace bank/blockchain/email evidence.

## Current deployment status

Code support is prepared in the candidate branch. No paid GPU service has been provisioned and no live production backend has been switched automatically.

A CLM endpoint requires an encoder-serving runtime (official quickstart uses Qwen3-8B pooling through vLLM) plus `clm-serve`. Deployment is a separate resource/cost decision and must pass the existing infrastructure budget rule.
